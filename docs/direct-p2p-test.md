# STUN 없이 직접 P2P 테스트

## 현재 범위

원격 공유 화면의 STUN 입력란은 기본적으로 비어 있으며, 비워 두면 외부 ICE 서버를 설정하지 않습니다.
TURN 중계는 연결 방식에서 **TURN**을 선택하고 접속 정보를 입력해 설정합니다. 시그널링 WebSocket 서버는 Offer/Answer/ICE만 전달하고,
파일은 WebRTC DataChannel의 ICE/DTLS/SCTP 경로로 전송합니다.

한국어와 영어는 원격 공유 화면 상단에서 각각 선택합니다. 언어 선택은 전송 프로토콜에 영향을 주지 않습니다.

## STUN 연결

연결 방식에서 **직접 연결**을 고르고 STUN 서버 주소 칸에 `stun:서버:포트`를 한 줄에 하나씩 입력합니다. 비워 두면 같은 네트워크 안에서만 연결됩니다.
STUN 서버가 알려 준 공유기 바깥 주소(`srflx` 후보)로 직접 연결을 시도하며, 중계 서버는 쓰지 않습니다.
SIPSorcery는 ICE 서버를 한 번에 하나만 쓰므로, 두 번째 줄부터는 앞 서버가 실패했을 때만 사용됩니다.
**연결 환경 확인**으로 `typ srflx` 후보가 수집되는지 먼저 확인합니다. 진단 보고서에는 `STUN:` 뒤에 사용한 주소가 표시됩니다.

**STUN 먼저, 실패하면 TURN**으로 연결하려면 **서버를 통한 연결(TURN)**을 고르고 **항상 중계 서버 사용**을 끕니다.
TURN 서버도 공유기 바깥 주소를 알려 주므로 내 PC 주소, 바깥 주소, 중계 주소를 한 번에 시험하고, ICE가 직접 경로를 우선 선택합니다.
연결 후 실제 경로가 **직접 P2P**인지 **TURN 중계**인지 화면에서 확인합니다.

### 현재 가능한 ICE / TURN 테스트

1. TURN이 필요하면 아래 접속 정보를 입력합니다. 직접 연결만 테스트하려면 연결 방식을 **직접 연결**로 선택합니다.
2. **연결 경로 테스트**을 눌러 후보와 수집 상태를 확인합니다. 시그널링 서버 없이 실행되며 최대 20초 후 수집 결과를 유지합니다.
3. 실제 연결에는 양쪽이 접근 가능한 시그널링 서버와 같은 방 ID를 사용하고 내 기기 ID와 상대 기기 ID를 서로 바꿔 입력합니다.
4. 수신 쪽을 먼저 **연결 대기**로 연결한 뒤 송신 쪽을 **연결 시작**으로 연결합니다.
5. 선택된 후보 쌍과 `DataChannel: open`을 확인한 후 파일을 양방향 전송하고 SHA-256 통과까지 확인합니다.
6. 실패하면 **진단 결과 저장**으로 양쪽 결과를 저장합니다. 보고서에는 후보 IP 주소가 포함됩니다.

### TURN / Cloudflare 접속 정보 입력

기본 모드는 자동 발급입니다. [Cloudflare TURN 자동 연동 설정](cloudflare-turn-setup.md)에 따라
서버를 설정하고 앱에서 로그인하세요. 아래 항목은 자동 받기를 끈 수동 모드 안내입니다.

- 연결 방식에서 **TURN**을 선택하고 발급된 `urls`를 **TURN 주소**에 한 줄에 하나씩 입력합니다.
  `turn:turn.cloudflare.com:3478?transport=udp`, `turns:turn.cloudflare.com:443?transport=tcp` 같은 형식을 지원합니다.
- 발급된 `username`을 **TURN 사용자 이름**, `credential`을 **TURN 자격 증명**에 입력합니다.
  같은 자격 증명을 사용하는 주소만 함께 입력합니다. 자격 증명은 화면 메모리에만 보관하며 파일에 저장하지 않습니다.
- **TURN 중계만 사용**을 선택하면 `iceTransportPolicy=relay`로 후보 수집과 연결을 수행합니다.
  선택하지 않으면 직접·중계 후보를 함께 허용합니다. 중계 전용 옵션은 TURN을 선택했을 때만 표시되며 직접 연결에는 적용되지 않습니다.
- 먼저 후보 수집에서 `relay` 후보를 확인하고, 양쪽을 연결한 뒤 실제 전송 경로 **TURN 중계**와 파일 해시 검증을 확인합니다.
  실제 TURN 성공은 서버 접근성, 자격 증명, 만료 시점과 네트워크 조건에 따라 달라집니다.
- Cloudflare의 장기 TURN 키/API 토큰은 서버에서 단기 자격 증명을 발급하는 용도입니다. 앱에는 발급 결과만 입력합니다.
  자동 발급 모드는 연결·환경 확인마다 새 정보를 받습니다. 진행 중 세션의 자격 증명 갱신은 지원하지 않으므로 만료 전에 재연결하세요.
  [Cloudflare 공식 자격 증명 발급 안내](https://developers.cloudflare.com/realtime/turn/generate-credentials/)

DataChannel 및 파일 전송 구현과 로컬 통합 검증은 제공되지만, 실제 서로 다른 네트워크의 성공 여부는 이 절차로 확인해야 합니다.

## 1. 먼저 직접 전송 경로 확인

1. 두 창 또는 같은 LAN의 Windows PC 두 대에서 앱을 실행합니다.
2. 두 피어 모두 접근할 수 있는 같은 시그널링 서버 주소를 입력합니다.
   같은 PC 두 창만 `ws://localhost:5047/signal`을 사용합니다.
   별도 PC에서는 시그널링 서버 PC의 실제 접근 가능한 주소를 사용합니다.
3. STUN은 양쪽 모두 비워 두고 연결 방식을 **직접 연결**로 선택합니다. 두 기기 ID는 서로 다르게, 방 ID는 같게 설정합니다.
4. 수신 쪽은 **연결 대기**, 송신 쪽은 **연결 시작**으로 연결합니다.
5. 연결 후 실제 전송 경로가 **직접 P2P / Direct P2P**로 표시되는지 확인합니다.
6. 한쪽에서 파일을 보내고 반대쪽에서 저장 위치를 선택해 승인합니다.
7. 수신 완료·SHA-256 검증 통과를 확인하고 반대 방향으로도 전송합니다.

이 검증은 HTTP 파일 서버를 사용하지 않습니다. 같은 LAN에서 HTTP 공유와 사용자 기능이 비슷하더라도,
여기서 검증하는 전송 경로는 WebRTC입니다. 다만 이 결과가 인터넷의 NAT 통과 성공을 뜻하지는 않습니다.

## 2. 서로 다른 네트워크로 확장

예를 들어 PC A는 집 유선 인터넷, PC B는 휴대폰 핫스팟에 연결합니다. 두 PC는 공통 Wi-Fi나
별도 VPN을 공유하지 않아야 합니다. 양쪽이 접근 가능한 공용 시그널링 주소를 동일하게 사용합니다.
`localhost`나 집 내부의 사설 주소는 외부 PC에서 해당 서버에 도달할 주소가 아닙니다.

STUN 없는 테스트에서는 **실제로 상대가 접근할 수 있는 주소가 ICE 후보로 교환되어야** 합니다.
해당 인터페이스의 공인 주소 또는 접근 가능한 글로벌 IPv6 후보가 교환되는 환경이라면
직접 연결을 시도할 수 있습니다. 양쪽 NAT·방화벽·후보 수집 조건에 따라 실패할 수도 있습니다.

현재 앱에는 공유기 외부 주소를 수동 ICE 후보로 추가하거나 UDP 포트를 고정해 매핑하는 기능이 없습니다.
시그널링 서버의 TCP 포트만 열어 두는 것으로 파일 전송용 UDP 경로까지 만들어지지는 않습니다.
집 공유기와 모바일 CGNAT 뒤의 일반적인 두 PC가 사설 후보만 교환한다면, 현재 설정으로는
서로 다른 네트워크의 직접 연결을 기대하기 어렵습니다.

## 결과 구분

| 결과 | 확인한 내용 |
| --- | --- |
| 같은 PC/같은 LAN + 직접 P2P + 파일 해시 통과 | WebRTC 연결 및 파일 프로토콜 검증 |
| 서로 다른 네트워크 + 직접 P2P + 파일 해시 통과 | 해당 두 네트워크 사이의 직접 파일 전송 검증 |
| 시그널링만 연결되고 피어 연결 시간 초과 | 기기 ID·방·상대 준비 상태와 후보의 실제 도달 가능성 확인 필요 |

위 직접 연결 테스트는 TURN을 끈 상태이므로 중계 경로를 사용하지 않습니다. HTTP로 자동 전환하지도 않습니다.
STUN/TURN을 사용한 결과와 비교해 NAT 통과 범위를 확인합니다.

참고: [WebRTC의 시그널링과 ICE 후보 설명](https://webrtc.org/getting-started/peer-connections).
